# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Monks Internal Management: internal app for Hybrid Monks LLP (accounting, employees, invoices, salaries, attendance, reports). npm workspaces: `client/` (React 19 + Vite + Tailwind 4) and `server/` (Express 5 + TypeScript, plain `pg`, plain SQL migrations). One Node process serves `/api` and, in production, the built client.

## Commands (run from the repo root)

```sh
npm run dev                  # server :4000 (tsx watch) + client :3000 (Vite, proxies /api → :4000)
npm run lint                 # tsc --noEmit for both workspaces (there is no ESLint/Prettier)
npm run lint -w client       # type-check one workspace
npm run lint -w server
npm test                     # server vitest + supertest suite (needs Postgres running)
npm test -w server -- test/auth.test.ts   # single file
npm test -w server -- -t "login"          # tests whose name matches
npm run db:migrate           # apply pending server/db/migrations/*.sql
npm run db:seed              # load server/db/seed.dev.sql (refuses if users exist, or if the DB host is not localhost, 127.0.0.1, ::1 or db)
npm run db:seed -- --reset   # wipe app data and reseed
npm run build                # client/dist + server/dist
npm run create-admin -w server -- --email you@example.com   # create an admin (hidden password prompt; how the first production admin is made)
npm run link-by-email        # dry run: employee records and staff logins with the same email that aren't linked (-- --apply links them)
npm run check-accounts -- --plan "name=role,..."   # read-only: every login, role, linked employee, last login, and flags
```

## Rules

- Never edit an applied migration; always add a new numbered one (a hook blocks edits to existing files in `server/db/migrations/`).
- Money is `NUMERIC(14,2)` in Postgres and travels as a string, never a JS float. Invoice arithmetic lives only in `server/src/services/money.ts` (BigInt paise; `computeTotals`, `moneyAmount`/`quantityValue`/`percentValue` zod helpers). The browser never computes stored amounts: it shows server strings with `formatMoney()` (`client/src/utils/money.ts`); the invoice form's `previewTotals()` is a labelled live preview only.
- **Every route declares its roles** (deny by default): routes are added only through `createRouter()` from `server/src/middleware/access.ts` — `router.get(path, access, ...handlers)` where `access` is `'public'`, `'session'` (only `/auth/me`, `/auth/logout`, `/auth/change-password`) or a role list such as `['admin', 'manager']` or `STAFF` — and routers are mounted with `mountRouter()`. `server/test/route-matrix.test.ts` walks every registered route and fails if one bypasses this, if a client session can reach anything outside its allowlist, or if a non-public route answers an anonymous caller. UI checks are cosmetic only.
- **Out-of-scope ids are 404, never 403:** when a record exists but belongs to someone else (another employee's task, another company's project), answer exactly like a missing id so nothing leaks. 403 is only for "your role can't do this at all".
- **Client portal API** lives in `server/src/routes/portal.ts` under `/api/portal`, every route `['client']`, scoped by `clientScope(req)`; clients only see `client_visible` tasks of their company's non-archived projects, may request tasks on those projects assigned to that project's active team (no admin/manager logins; `tasks.requested_by_client`, migration 014; editable by the client only while `todo`, else 409 `TASK_LOCKED`; staff can't hide them, 409 `CLIENT_REQUEST_VISIBLE`; the admin/manager bell lists open requests; `server/test/portal-tasks.test.ts`), only `client_feedback` comments (filtered in SQL), and their company's issued invoices (`/api/portal/invoices(/:id)`: sent, paid or cancelled, never drafts; no cancel reason, payment notes/references, recorder or reversed payments; `server/test/portal-invoices.test.ts`). Portal responses select an explicit column list with no internal fields; `server/test/portal.test.ts` asserts on the raw JSON text that internal notes never appear.
- **Client scoping:** a `client` user sees only their own company. Client-scoped queries take the company from `clientScope(req)` (= `req.user.clientId`), never from the body, query string or URL. Clients never see finance (salary, ledger, reports, the staff invoice API), employee records or other clients; the only money they see is their own company's issued invoices through the portal. Adding a client-visible route means adding it to the allowlist in `route-matrix.test.ts` on purpose.
- No passwords, set-password links or tokens in logs, API responses or audit metadata. The only exception is the dev mail printout in `server/src/services/mail.ts`.
- **Passwords are used exactly as typed**: never trim or normalise a password, on the client or the server (spaces anywhere are valid and count towards the 10-character minimum; only an all-whitespace password is refused). Emails are trimmed and matched case-insensitively (citext). Password inputs use `PasswordField` (`components/auth/AuthLayout.tsx`: show/hide, no autocapitalise/autocorrect/spellcheck).
- **Managers see no money.** Every money route (`/api/invoices`, `/api/settings`, `/api/transactions`, `/api/reports`, `/api/salary` except the own-payslip routes) is `['admin']` (`route-matrix.test.ts`), and `server/test/manager-no-money.test.ts` calls every GET route a manager can reach and fails on any money-ish key or decimal amount. Payloads for managers drop money fields on the server (`forViewer()` in `routes/employees.ts`), not just in the UI.
- Do not add new npm libraries without asking first.
- Don't edit `.env` or `package-lock.json` (also blocked by a hook).

- `.env` lives at the repo root (loaded by `server/src/config.ts`, validated with zod; the server exits on invalid config). It holds the real `SESSION_SECRET` and `DATABASE_URL` — don't edit it.
- Seed logins (password `devpass123`): `admin@example.test`, `manager@example.test`, `employee1@example.test`, `employee2@example.test`. EMP-004 is an employee without a login, for testing "Add user".
- Every email is built by `composeMail()` (`services/mail.ts`): a plain-text and an HTML part from the same words, one link shown as itself on `APP_URL`, a short plain subject, no images or tracking (Resend open/click tracking stays off), and `Reply-To: SMTP_REPLY_TO` when that optional variable is set.
- Mail transport (`server/src/services/mail.ts`): Resend's HTTPS API when `RESEND_API_KEY` is set (production on Render, whose free tier blocks SMTP), else SMTP when `SMTP_HOST` is set. Every send has a 10 s timeout; a failed invite or admin reset-link email is 502 `MAIL_FAILED` with nothing left usable (mail is sent after the DB transaction commits; the route then deletes what it created). Logs carry only purpose, transport and code. Tests use `setMailTransportForTests()` with a mocked fetch (`server/test/mail.test.ts`).
- With neither `RESEND_API_KEY` nor `SMTP_HOST` set (dev), every email — invite and reset links — is **printed to the server console** instead of sent. In tests, mail goes to `testOutbox` in `server/src/services/mail.ts`.

## Architecture

### Migration in progress: localStorage → Express + Postgres

The app started as a client-only prototype storing everything in localStorage. Auth, users, **employees**, clients, projects/tasks, **attendance, presence and leaves**, **invoices (with their payments) and company settings**, **salaries and payslips**, **the ledger (transactions, categories) and reports** are now server-side; only the activity/audit logs still live in `client/src/services/storage.ts` (`StorageService`) and are wired through `client/src/context/AppContext.tsx`. Each phase moves one domain to the server. **Employees is the reference pattern** to copy:

- **Server route**: `server/src/routes/employees.ts` — `createRouter()` with an explicit access list on every route, zod schemas validated via `parseBody()` (unknown keys are stripped; use `.strict()` where extra fields must be rejected), ids parsed with `z.uuid()` (invalid → 404), `HttpError(status, message, CODE)` for failures, `withTransaction()` for multi-statement writes with `FOR UPDATE` locking, `audit(req, {...})` after successful mutations (field names, never values like salaries). Unique violations (`23505`) become 409s. Static paths (`/directory`, `/me`) are declared before `/:id`. Mounted in `server/src/app.ts`.
- **Role-scoped fields**: fields only admins may see (salary: `monthlySalary`, `paymentMethod`) are deleted from the response object for other roles, not nulled (`forViewer()` in `routes/employees.ts`).
- **Never deleted**: records are deactivated/reactivated; there is no DELETE route. Codes like `EMP-001` are assigned by the server (max+1 under `pg_advisory_xact_lock`).
- **API shapes are the client types**: `client/src/types/index.ts` mirrors the JSON (camelCase, lowercase status values like `'on_leave'` with a `*_LABEL` map for display, money as decimal strings). Don't map to old prototype shapes.
- **Audit actions** are a closed union type in `server/src/services/audit.ts`; add new action strings there. Never put passwords or tokens in metadata.
- **Client API module**: `client/src/api/employees.ts` — thin typed wrappers over `api()` in `client/src/api/client.ts`, which throws `ApiError` (with per-field `details` for 400s) and triggers the session handlers on 401 `UNAUTHENTICATED` / 403 `PASSWORD_CHANGE_REQUIRED`.
- **Page data**: each page fetches its own data with `useApiData(load, deps)` (`client/src/api/useApiData.ts`) and renders loading / `LoadError` / `EmptyState`; nothing server-backed goes into `AppContext`. Forms show server validation errors with `common/FormField`.
- **Tests**: `server/test/employees.test.ts` — a role matrix (admin/manager/employee/anonymous) per route, then behaviour tests; `createUser(email, role, employeeId)` + `signIn()` (a `request.agent(app)`), `TRUNCATE ... CASCADE` in `beforeEach`, assertions on `audit_logs` rows.

### Client routing (`client/src/App.tsx`, `client/src/routes/guards.tsx`)

- react-router v7 (`import from 'react-router'`). Pages are `React.lazy` chunks rendered inside `MainLayout`'s `<Outlet/>`.
- `RequireAuth` (→ `/login` with `state.from`, → `/change-password` while `mustChangePassword`), `RequireRole roles={[...]}` (→ `/dashboard` + toast), `RedirectIfSignedIn` for `/login` and `/forgot-password`.
- Detail views are routes that open a modal over the list (`/employees/:id`, `/invoices/:id`); the modal loads its own record so deep links work.
- Sidebar items are role-filtered `NavLink`s in `components/layout/Sidebar.tsx` (cosmetic; the server is the guard).
- **Two shells:** staff use `MainLayout` (wrapped in `RequireStaff` + `AppProvider`); `client` users use `/portal` (`ClientPortalLayout`, wrapped in `RequireClient`, no `AppProvider`, so no staff/localStorage data is ever loaded for them). A client opening any staff URL lands on `/portal`; staff opening `/portal` land on `/dashboard`. Login return paths are only honoured within the user's own shell (`safeReturnPath` in `routes/guards.tsx`).
- Work routes: `/projects(/:id)` and `/tasks(/:id)` (admin, manager), `/my/tasks(/:id)` and `/my/projects(/:id)` (employee; same `TasksView`/`ProjectsView` components in "mine" mode), `/portal`, `/portal/projects(/:id)`, `/portal/invoices(/:id)` (the printable invoice, same `InvoiceDocument`), `/portal/team` (client). Attendance and leaves: `/attendance`, `/leaves` (admin, manager), `/my/attendance`, `/my/leaves` (employee). Ledger: `/accounting` and `/accounting/new` (admin). Invoices `/invoices...` and reports `/reports`: admin only (managers have no Invoices or Reports item). Dashboard: managers get `OperationsDashboard` only; admins get two tabs, Overview (`FinanceOverview`) and Operations (the same `OperationsDashboard`), with `?tab=operations`. Salary: `/salary` (admin; `?month=YYYY-MM` opens that month); own payslips `/salary/slips(/:id)(/print)` for any staff login linked to an employee (sidebar "My Payslips"; managers have no Salary item). Task status changes go through `components/work/TaskStatusControl.tsx`, which mirrors the server rules (`EMPLOYEE_TASK_TRANSITIONS` in `types/work.ts`). Project/task/portal types live in `client/src/types/work.ts`.
- **Tasks between colleagues and the bell:** an employee sees tasks assigned to them and tasks they assigned (`tasks.created_by`); they may create tasks on projects they are on for any active colleague (never `clientVisible`), edit/delete their own only while `todo` (else 409 `TASK_LOCKED`, someone else's 403), and review a colleague's hand-over (`in_review` → `completed`/`in_progress`, `CREATOR_TASK_TRANSITIONS` / `allowedTaskMoves` in `types/work.ts`). `GET /api/tasks?view=assigned_by_me` ("Assigned by me" on My Tasks). Setting or changing an assignee (staff or portal) writes a `notifications` row (migration 015, `services/notifications.ts`) for the assignee's staff logins, never the actor. `GET /api/notifications` (`routes/notifications.ts`) returns those plus derived reminders (own open tasks due today/tomorrow/overdue; overdue tasks of others: admin/manager all, employee the ones they assigned); the TopNav bell polls it every 60 s. `server/test/task-assignment.test.ts`.
- Creating logins: `components/users/AddUserModal.tsx` (shared by Settings > Users and the client detail panel; managers only get the client role). Linking a login to an employee: `components/users/LinkAccountModal.tsx` (Settings > Users "Link employee" and the Employees row action).
- **Employee <-> login links** (`users.employee_id`, UNIQUE): `services/accountLinks.ts` links an employee and a staff login with the same email (citext) automatically on employee create, on a work-email change and on staff user create; never a client user, never an inactive employee, never moving an existing link. Admins link/unlink by hand with `PUT/DELETE /api/users/:id/employee` (409 `EMPLOYEE_LINKED`/`USER_LINKED`, 400 `CLIENT_USER`, 400 `CANNOT_MODIFY_SELF`: nobody re-links their own login, whose employee id is what `CANNOT_MODIFY_OWN`/`CANNOT_CORRECT_OWN` rely on). Audited as `user.employee_linked` (`how: email | manual | script`) / `user.employee_unlinked`.
- `currentUser` (AppContext) comes from the session (`/api/auth/me`, which includes the linked employee's name, designation, department, avatarUrl); `currentUser.employeeId` is the employee uuid.

### Auth and sessions (`server/src/middleware/auth.ts`, `server/src/session.ts`)

- Cookie sessions stored in Postgres (`sessions` table via connect-pg-simple). The user is reloaded from the DB on every request, so disabling a user or changing a role takes effect immediately; `deleteUserSessions()` signs a user out everywhere. Sessions have an **absolute 12-hour lifetime** from login for every role (`SESSION_LIFETIME_MS` in `session.ts`, `req.session.loginAt` checked in `requireSession` against the server clock); activity and heartbeats never extend it (the cookie is not rolling), and a password change keeps the original login time.
- `requireSession` = signed in. `requireAuth` = `requireSession` + the forced-password-change gate. Routes don't use these directly: `createRouter()` applies them from the declared access (`'session'` → `requireSession`; a role list → `requireAuth` + `requireRole`).
- Roles: `admin`, `manager`, `employee`, `client` (portal users of a client company, `users.client_id`), enforced only by the server. A client user of an inactive company is treated as signed out (`loadSessionUser`) and can't log in. Managers may create and manage client users only.
- `checkOrigin` (`server/src/middleware/security.ts`) rejects mutating requests from foreign origins (CSRF defence alongside SameSite=Lax). Every rate limit is in the `RATE_LIMITS` table there (built with `createLimiter`, per IP, per user or per target email; skipped in tests unless a test builds its own). Every public route and every route that sends email must carry one: `route-matrix.test.ts` checks it (add new mail-sending routes to its `SENDS_EMAIL` list).
- `TRUST_PROXY` (production only; `app.set('trust proxy')`) is the number of reverse proxies in front of the app: **2 behind Vercel + Render**, **1 behind a single proxy** (Render alone, or nginx/Caddy in front of docker-compose). It picks which `X-Forwarded-For` entry is `req.ip` (rate limits, request logs) and makes `X-Forwarded-Proto` count for secure cookies. Too low: every user shares one rate-limit bucket; too high: clients can choose their IP. Documented in `.env.production.example`.
- Invite-only accounts: admins (managers: client users) create users with **no password** (`password_hash` NULL, shown as "Invited"; such an account can never sign in with a password) and the server emails a one-time link `{APP_URL}/set-password?token=...`. Links live in `password_tokens` (migration 010; `services/passwordTokens.ts`): 32 random bytes base64url, only the SHA-256 stored, invite 72 h, reset 1 h, single use (one `UPDATE ... WHERE used_at IS NULL AND expires_at > now() RETURNING`). Forgot-password and the admin "Send reset link" use the same table and page. A new link replaces older unused ones (admin actions drop them only after the email went out); setting or changing a password deletes all outstanding links and ends every other session. `GET /api/auth/set-password/check` and `POST /api/auth/set-password` are public, rate limited per IP and per token hash prefix, and answer every bad link with the same 400 `LINK_INVALID` (unknown, expired, used, replaced, disabled account); the POST signs the browser in. The client page `/set-password` strips the token from the URL at once. `must_change_password` (→ `/change-password`) remains only for accounts that still have a temporary password from before invite links.

### Invoices and company settings

- Routes: `server/src/routes/invoices.ts` (`/api/invoices`) and `routes/settings.ts` (`/api/settings/company`). Admin only (managers, employees and clients get 403). Clients read their own issued invoices through `/api/portal/invoices`.
- Lifecycle: `draft` (no number; all editable, may be deleted) → `send` → `sent` (number assigned now; client and lines locked; only `dueDate` and `notes` change) → `paid` (automatically, in the same DB transaction, when payments reach the total). Draft or sent invoices without payments can be cancelled (admin, reason); cancelled invoices keep their number if they had one (a cancelled draft never gets one). Paid/cancelled → 409 `INVOICE_LOCKED`.
- Numbers: `company_settings.invoice_prefix` + `invoice_next_number` (zero-padded to 4, e.g. `HM-0007`), assigned at **send** (`takeInvoiceNumber`) under `SELECT ... FOR UPDATE` on the settings row, skipping numbers already taken, so deleted or cancelled drafts consume none and there are no gaps. `invoice_number` is NULL for drafts (rows from before migration 007 keep theirs). Numbers are never changed or reused. The UI shows `invoiceLabel()` (`types/invoices.ts`): the number, or "Draft". A prefix change only affects new numbers.
- Payments are `transactions` rows (`type 'income'`, category `Invoice Payment`, `invoice_id` set). Amount must be > 0 and ≤ balance (409 `OVERPAYMENT`), dated between the invoice date and today (IST). Reversal (`DELETE /:id/payments/:txnId` with `{ reason }`) keeps the row and marks it reversed (`reversed_at/by`, `reverse_reason`; 409 `ALREADY_REVERSED` the second time); paid → sent; the audit row keeps amount, date, method and reference. The detail lists reversed payments struck through.
- Derived, never stored: `amountPaid`, `balance`, `derivedStatus` (`overdue` = sent, balance > 0, due date before today IST; wins over `partially_paid`). List filters accept the derived values plus `outstanding`; the list `summary` covers all invoices.
- **Currency** (migration 013, `services/currency.ts`): each invoice has a `currency` (default: the client's `clients.currency`, else INR); all its amounts, payments and balance are in it. A payment stores `transactions.invoice_amount` (invoice currency, counts towards the balance) and `amount` (the INR received, what the ledger/P&L sum; `amountInr` in the API, required for non-INR invoices). Sums never mix currencies: list/portal summaries give INR in `outstandingTotal`/`overdueTotal` and other currencies in `otherCurrencies`; the invoice report takes `?currency=`. Company settings also hold the signature image and signatory name/designation printed on invoices.
- `client_id` links an invoice to a client company, but `client_name/email/address/gstin` are a snapshot taken when the invoice is written (fields sent in the request override the client's), so later client edits never change an invoice.
- Client UI: `/invoices`, `/invoices/new`, `/invoices/:id`, `/invoices/:id/edit` (modals over the list) and `/invoices/:id/print` (A4 sheet; the app chrome carries `no-print`, see `.invoice-sheet` in `index.css`). Settings > Company edits the settings (admin). Screens all roles see use `COMPANY_BRAND` (`utils/company.ts`) and `CURRENCY` (INR) instead of settings, because employees can't read `/api/settings`.

### Salary and payslips

- Routes: `server/src/routes/salary.ts` (`/api/salary`), admin only except `GET /slips/me` and `/slips/me/:id` (employee, manager, admin), which select by `req.user.employeeId` only: another person's slip, an unpublished one or a missing id are the same 404; a login without an employee gets 403 `NOT_LINKED`. The slip response is an explicit object (own employee name/code/department/designation, company name/address, base, lines, adjustments, net, paid date/method).
- One `salaries` row per employee per month. `POST /generate { month }` (at most one month ahead) inserts missing rows for active/on-leave employees with `monthly_salary > 0` who joined by the month's last day; `base_salary` is a snapshot. Idempotent (`ON CONFLICT DO NOTHING`).
- Itemised `salary_adjustment_lines` (earning/deduction, amount > 0); `salaries.adjustments` is their stored sum and `net_payable` a generated column. All arithmetic is in `server/src/services/salary.ts` (BigInt paise): a change that would make the net negative is 409 `NEGATIVE_NET`. Lines, notes and a base override (reason required, recorded in the audit row) only while pending (409 `SALARY_LOCKED`). Nobody changes their own salary row (the row whose employee is `req.user.employeeId`): lines, base/notes, pay, unpay and slip publish/unpublish answer 400 `CANNOT_MODIFY_OWN` (checked in `lockSalary`, after the 404); another admin can.
- `POST /:id/pay` creates exactly one expense transaction (category `Salary`, `salary_id`, amount = net) and sets paid in one DB transaction; a partial unique index (`transactions_salary_id_live_key`) allows one live row per salary. `/unpay { reason }` marks that row reversed and returns to pending, clearing paid date, method and the slip. Slips are published only while paid.
- Audit metadata: ids, month, status changes, line kind; never amounts. The browser shows server amounts only; the adjustment form's `previewNetAfterLine()` (`utils/money.ts`) is a labelled preview.
- Client: `client/src/api/salary.ts`, `types/salary.ts`, `components/salary/` (`SalaryView` + `SalaryDetailModal` for admins; `EmployeeSalarySlipsView`, `PayslipDocument`, `PayslipPrintView` reusing `.invoice-sheet`). Dashboard and top bar read `/api/salary` for admins only; the Reports salary tab reads `/api/reports/salary`.

### Ledger and reports

- Ledger routes: `server/src/routes/transactions.ts` (`/api/transactions`, **admin only**). Every money movement is a `transactions` row: invoice payments (income, `invoice_id`), salary payments (expense, `salary_id`) and manual rows. Linked rows are owned by their invoice or salary: PATCH/void answer 409 `LINKED_TRANSACTION` with the owner in `details` (`type`, `invoiceId`/`invoiceNumber` or `salaryId`/`salaryMonth`). Manual rows are created, edited and voided (`POST /:id/void { reason }`, the reversed_* columns); **there is no DELETE route**. The list takes `type, category, from/to or preset, paymentMethod, source (manual|invoice|salary), search, includeVoided` and returns SQL totals for the whole filtered set, never counting voided/reversed rows. `GET /export.csv` takes the same filters.
- Categories: `transaction_categories` (citext unique names, income/expense, `is_system`, `active`). Transactions keep a text `category` (no FK); the API checks a manual row's category exists, is active (an edited row may keep its own inactive one), matches the type and isn't a system one ("Invoice Payment", "Salary"). Renaming rewrites the text on manual rows in the same DB transaction (409 `CATEGORY_LINKED` if invoice/salary rows use the name); system categories can't be renamed or deactivated. Deactivated categories are hidden from pickers.
- Reports: `server/src/routes/reports.ts` (`/api/reports`), read-only. `profit-loss` (cash basis, by `txn_date`), `trend?months=1..24` and `salary` are admin only; `invoices` (status summary for invoices dated in the period, aging buckets and top outstanding as of today, top clients) is admin only too and carries no ledger or payment-method data. Every figure is summed in SQL on NUMERIC and sent as a 2-decimal string; voided/reversed rows are always excluded.
- **Periods** come only from `server/src/services/period.ts` (`resolvePeriod`): presets `this_month`, `last_month`, `this_fy`, `last_fy` (from the IST date and `company_settings.financial_year_start_month`) or `from`+`to`; mixed, half, reversed or over-5-year ranges are 400. Reports default to `this_fy`; the ledger accepts `preset` too.
- **CSV** comes only from `server/src/services/csv.ts` (`toCsv`, `sendCsv`): RFC 4180, UTF-8 BOM, CRLF, a leading `'` on any cell starting with `= + - @` TAB or CR (negative amounts included), at most `CSV_ROW_CAP` (50,000) rows with `X-Row-Cap-Reached`, a filename from fixed text and the server date. Every export is audited (`export.downloaded`: which export, filters, row count; a free-text search only as `true/false`).
- Client: `api/transactions.ts`, `api/reports.ts`, `types/ledger.ts`; `components/accounting/` (`AccountingView`, `TransactionModal`, `CategoriesManager`), `components/reports/` (`ReportsView`, `TrendBars`: pure-CSS bars plus a table), `common/PeriodPicker`. The admin dashboard's Overview tab (`FinanceOverview`) reads `/api/reports/profit-loss` and `/trend`; `OperationsDashboard` (managers, and the admin's Operations tab) never calls a money API. Bar heights use the display-only helpers `sharePercent()`/`maxAmount()` (`utils/money.ts`); no amount shown is computed in the browser.

### Database

- Shared route helpers: `server/src/routes/shared.ts` (`optionalText`, `isoDate`, `pageQuery`, `likePattern`, `TODAY_SQL`). "Overdue" is always derived (`status <> 'completed' AND deadline < TODAY_SQL`, Asia/Kolkata), never stored; names (project, assignee, client) are joined, never copied onto rows.
- **Time and "today":** attendance, presence and leave code reads time only through `server/src/services/clock.ts` (`now()`, `istDate()`, `todayIst()`, `countWeekdays()`), never `Date.now()` directly, Postgres `now()` for business timestamps, or the browser clock. Tests freeze it with `setClock()` / `resetClock()`. The client shows times with `formatTimeIst`, timestamps as dates with `formatDateIst` (never `iso.slice(0, 10)`, which is the UTC day), and takes "today" from API responses (`date`, `today`, `serverTime`).
- **Availability** (`on_leave | online | available | not_in_today`) lives only in `server/src/services/availability.ts` (`deriveAvailability` rules + `availabilityFor(ids)`); every screen that shows a status asks it, nothing stores it. Online = an open shift (or a record for today's working day) not punched out, heartbeat within 5 min; half-day leave does not count as on leave. The roster status uses the same rule via `dayStatus()` (approved full-day leave wins over a punch-in: `on_leave`, punch times still returned), and the Employees page "On Leave Today" card counts the same thing (`summary.onLeaveToday`). Employees whose login is an admin or manager get `status: null` (attendance not tracked for them) in `/api/team/availability` and `/api/portal/team`; the UI shows no badge/dot for null.
- **Working hours and the working day:** most shifts are at night (overseas clients). Every employee has working hours (`employees.shift_start/shift_end`, IST `time`, migration 012; the end may be earlier than the start for an overnight shift; required for new employees, 'HH:MM' in the API). Their **working day** starts `SHIFT_EARLY_BUFFER_MINUTES` (2 h) before the shift start (21:00 shift: 19:00-18:59), so an early sign-in counts and a 01:30 punch-in belongs to the evening's shift; an open record stays the **current shift** until `SHIFT_LATE_BUFFER_MINUTES` (3 h) after the shift end, after which it is "incomplete" (worked minutes null, not "working"). Employees without hours (created before them) use the default working day 06:00-05:59 IST (`workDate()` in `services/clock.ts`) and `MAX_SHIFT_HOURS` (16 h); admins are reminded to set them (`summary.withoutWorkingHours`, `GET /api/employees?workingHours=missing`, banners on Employees and the admin dashboard). All of it lives in `services/attendance.ts` (`employeeWorkDate`, `isOpenShift` and their SQL twins `employeeWorkDateSql`, `openShiftSql`); invoices, salary and the ledger keep the calendar `istDate()`.
- **Attendance:** one `attendance_records` row per employee per working day. A **shift** is one record from punch-in to an explicit punch-out, however many midnights it crosses: while an employee has an open shift no new record is created, and `/me/today` (which also returns `shift`), punch-out, worked minutes, the roster's "currently working" and availability all use it. Corrections must put the punch-in inside the employee's working day for that date. **Nothing punches anyone in automatically** (migration 016; signing in, heartbeats and page loads never create a record): an employee-role user with an active linked employee presses Punch In (`POST /api/attendance/me/punch-in`, `components/attendance/PunchInButton.tsx`, asks for confirmation; source `punch`; 409 `ALREADY_PUNCHED_IN` while a shift is open, `ALREADY_RECORDED` once the working day has a record). It is allowed at any time; `punchFlags()` (`services/attendance.ts`) derives `lateMinutes` (more than `LATE_AFTER_MINUTES` = 30 after the shift start) and `outsideHours` (outside the 2 h-early..shift-end window) on every record, never stored. `/me/today` returns `punchInDue` (window open, nothing recorded, no full-day leave) and `punchOutDue` (open shift past its end); the bell shows them, and admin/manager see the last 7 days of uncorrected forgotten punch-outs and outside-hours punches there and in `GET /api/attendance/review?days=` (the "Needs review" list; late ones too). **Only** `POST /api/attendance/me/punch-out` (the employee's own button, which asks for confirmation in `components/attendance/PunchOutButton.tsx`) and admin/manager corrections set `punch_out`: sign-out, heartbeats, closing the tab and session expiry never do. Managers/admins do not punch in (the route is employee-only), so the admin/manager roster (`GET /api/attendance`) leaves out employees whose login is an admin or manager (login-less employees stay in). `updated_by IS NOT NULL` means "corrected by an admin/manager"; corrections are audited with before/after values, and nobody corrects their own record (400 `CANNOT_CORRECT_OWN`). Heartbeats (`POST /api/presence/heartbeat`, `usePresence` in the staff layout) write `employees.last_seen_at` at most every 30 s, are not audited, and don't bump `employees.updated_at`.
- **Leaves:** `total_days` = weekdays only (half day 0.5), computed by the server; no overlap with the same employee's pending/approved requests; only pending requests can be edited/cancelled (owner) or reviewed (admin/manager, never their own: 400 `CANNOT_REVIEW_OWN`). Reasons are only returned to the owner, admins and managers; audit metadata never contains them.

- `server/src/db.ts`: `query()` and `withTransaction()`; all SQL is hand-written and must be parameterised (`$1`, `$2`…). `NUMERIC` comes back as a string (intended, for money); `DATE` comes back as `'YYYY-MM-DD'`.
- `server/src/migrations.ts` applies `server/db/migrations/NNN_name.sql` in filename order, each in a transaction, recording filenames in `schema_migrations`. **An applied file is never re-run, so never edit an existing migration — add a new numbered one.**
- **Ledger rows are reversed, never deleted:** `transactions.reversed_at/reversed_by/reverse_reason` (all null or all set). Every sum of payments filters `reversed_at IS NULL`.
- Schema conventions (see header of `001_init.sql`): uuid PKs (`gen_random_uuid()`), `citext` emails, money `numeric(14,2)`, text status columns with `CHECK (... IN (...))`, `created_at`/`updated_at timestamptz` on every app table with a `set_updated_at()` trigger. `audit_logs` is append-only (no `updated_at`).
- Snake_case columns are aliased to camelCase in SELECTs (`must_change_password AS "mustChangePassword"`).

### Tests

- Fixture helpers for multi-role scenarios: `server/test/fixtures.ts` (`resetAll`, `employee`, `company`, `user`, `signIn`, `project`, `task`, `comment`). Time-dependent tests call `setClock()` in `beforeEach` and `resetClock()` in `afterEach`.

Tests use the same `DATABASE_URL` but a separate Postgres schema **unique to each run**: `server/vitest.config.ts` sets `DB_SCHEMA=hm_test_<pid>`; `test/global-setup.ts` creates that schema, runs all migrations, and drops it at the end. Under `NODE_ENV=test`, `query()` in `db.ts` refuses TRUNCATE/DROP/DELETE unless `current_schema()` is the test schema (if it were missing, `search_path` would fall through to `public`; that once wiped the dev data when two runs shared one schema name). Never point tests at a fixed shared schema name. Files run serially (`fileParallelism: false`).
